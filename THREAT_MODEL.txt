================================================================================
THREAT MODEL - eBPF EDR AGENT
Architecture: Linux agent -> proxy -> offshore storage
================================================================================

SCOPE AND METHOD
--------------------------------------------------------------------------------
This document covers attack surfaces against the agent as it exists in this
repository, plus the architectural surfaces introduced by the proxy and offshore
storage tiers.

Threat model assumption: the attacker achieves root on the monitored host. This
is the correct assumption for an EDR. Every control below is judged by whether it
survives that, and most do not - which is expected. The goal is not prevention;
it is (a) making pre-compromise evidence unforgeable, (b) making tampering
detectable, and (c) making the act of attempting it noisy.

This document was assembled in two passes. The first was organised by component,
which is the defender's view. The second was organised by attacker objective,
which surfaced findings the first pass structurally could not see. Section 10
indexes every finding by attacker goal. Section 12 states the limits of this
document honestly.

FINDING COUNT: 58 total - 7 critical, 28 high, 21 medium, 2 low

  Section 1   NOW-1  to NOW-14   Present in the code on disk today
  Section 2   SEN-1  to SEN-10   Sensor / eBPF layer

HOW TO READ A FINDING
  Each finding is presented as:
      ID   NAME                                              [SEVERITY]
           ISSUE:     what an attacker does, and why it works
           SOLUTION:  the hypothetical remediation
  Findings marked (SELF) are defects in code written during the review process
  itself, not in the original codebase. They are included because a threat model
  that hides its own authorship errors is not a threat model.

COLLECTOR PASS - 2026-08-16
--------------------------------------------------------------------------------
A collector now exists (crate: edr-collector) together with an agent-side
shipper (edr-agent/src/shipper.rs). That converts a block of findings from
"nothing to fix" into "fixed", because they were never agent bugs -- they were
consequences of there being nothing off-box to remember anything.

  NOW-3 / STO-4  the collector keeps a per-host high-water seq. Tail truncation
                 is invisible on the host by construction: a chain with its last
                 N records removed verifies perfectly. It is a gap here.
  NOW-7          every record is stored with a collector-stamped received_at
                 alongside the agent's own timestamp.
  NOW-8          K0 is escrowed at the collector by the operator, out of band.
                 A wiped-and-restarted agent mints a new K0 and its records fail
                 here. Re-enrollment is refused without --force.
  PRX-1 / PRX-2  the proxy is explicitly untrusted. It never sees K0, cannot
                 forge a record, and cannot usefully replay one because seq must
                 advance. Dropping batches is the one attack it retains, which
                 is what silence detection is for.
  PRX-5          --silence-secs reports a host that stops sending. Silence is
                 the loudest signal this system has and it is only audible from
                 off-box.
  SUP-2          the agent reports its own dev:inode:mtime on every batch and
                 the collector compares it to what was enrolled. A binary
                 swapped for a heartbeating stub is caught.
  SEN-6          [PARTIAL -> still partial] read-side plausibility validation
                 now rejects events the kernel probe could not have produced
                 (impossible pids, zero or future ktime, empty comm, non-zero
                 reserved padding). This catches sloppy injection into the
                 pinned map and makes it noisy. It does NOT catch careful
                 injection: an attacker who reads the probe source can craft
                 values that pass. The finding stays open.

Note on scope: the collector closes these findings only for records that
actually reach it. Everything written while the network is down still sits on
the host, still forgeable by root, until it ships. That window is what the
forward-secure key evolution covers, and the two mechanisms are complementary
rather than redundant -- neither is sufficient alone. See Section 8.

Two new exposures the collector introduces, which did not exist before:

  ISSUE: The collector holds every enrolled host's K0.
  ------------------------------------------------
  Compromising it yields the ability to forge any host's entire history
  retroactively -- strictly more power than compromising any single agent. The
  anchor is now a single point of failure.
  SOLUTION: Treat it as higher-value than any host it watches. Longer term the
  ---------
  right answer is that the collector should not need K0 at all: publish periodic
  chain checkpoints to an append-only external witness (a transparency log, a
  second party's collector, or signed periodic anchors) so that verification
  does not depend on trusting whoever holds the escrow.

  ISSUE: The workspace builds release with panic = "abort", and the collector
  ------------------------------------------------------------------------
  parses attacker-influenced JSON on a network-facing path. One panic in a
  request handler takes the whole process down and blinds every enrolled host at
  once. The profile cannot be overridden per-crate.
  SOLUTION: The ingest path is written without unwrap, expect, indexing or
  ---------
  slicing on request-derived data, which is discipline rather than a guarantee.
  Either split the collector into its own workspace with panic = "unwind", or
  put a supervisor in front of it (Restart=always is set, which limits the
  outage to a restart rather than preventing it).

REVIEW PASS ON THE NEW CODE - 2026-08-16
========================================

Three defects found reviewing the collector against itself. All three are fixed;
they are recorded because each is a pattern worth not repeating.

  COL-1 (HIGH) Unbounded key derivation from an attacker-supplied field.
  ---------------------------------------------------------------------
  `epoch` arrives inside a record that has NOT been verified yet -- it cannot be,
  because the epoch is what selects the key to verify with. It was then used
  directly as a loop count, one SHA-256 per iteration. A single POST carrying
  epoch = 2^64-1 spins in the request handler while holding the mutex every other
  host needs. No forgery, no credentials, no access to any agent: one request
  blinds the entire fleet, and unlike a panic it never recovers.
  SOLUTION (applied): MAX_EPOCH_WALK caps derivation at ~2 years of agent uptime;
  --------
  anything beyond is refused as ImplausibleEpoch rather than computed. verify.py
  carries the same constant, because an investigator runs it against exactly the
  file an attacker just wrote -- hanging the verifier stops the investigation as
  effectively as deleting the records.
  GENERAL LESSON: a value taken from unverified input and used as a loop count,
  an allocation size or an index is a denial of service until it is bounded.

  COL-2 (MEDIUM) Storage failure permanently lost the batch it failed on.
  ----------------------------------------------------------------------
  In-memory state advanced per record as the batch was processed, then the append
  to disk failed and the handler returned without rolling back. The agent's retry
  hit the "already seen this seq" branch and the batch was discarded forever. One
  transient ENOSPC silently destroyed telemetry that both sides believed was
  safe. The acked value returned on that path was also computed as
  `high_seq - accepted`, which is wrong whenever seq is not dense -- it could ack
  past records that were never written.
  SOLUTION (applied): snapshot the state before the batch, restore it on write
  --------
  failure, and ack the snapshot's high-water mark.

  COL-3 (LOW) verify.py aborted on a tampered field instead of reporting it.
  -------------------------------------------------------------------------
  A non-numeric `seq` or `epoch` reached a comparison and raised TypeError,
  ending the run with a traceback at the first bad record rather than an alert.
  An attacker who cannot forge a record can still make the verifier fall over.
  SOLUTION (applied): type and range check both fields before use; report and
  --------
  return False like any other integrity failure.

CORRECTION TO EXISTING CODE
================================================================================
--------------------------------------------------------------------------------
THE "|" DELIMITER IN chain_hash() IS AMBIGUOUS                            (SELF)
--------------------------------------------------------------------------------
ISSUE:
  process_name is attacker-controlled - they choose the binary name - and a name
  containing "|" shifts field boundaries within the hashed payload.

      process_name = "bash|sshd", parent = "x"
      process_name = "bash",      parent = "sshd|x"

  Both produce an identical digest. Two distinct records can therefore be
  substituted for one another without breaking verification.

SOLUTION:
  Length-prefix each field - write a u32 length, then the bytes - instead of
  relying on a delimiter that can occur in the data. verify.py must mirror the
  change exactly.


================================================================================
PREFACE - THE ATTACKER'S FIRST MOVE
================================================================================

--------------------------------------------------------------------------------
DISC-1  THE AGENT IS TRIVIALLY DISCOVERABLE                             [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  Before attempting any evasion or tampering, an attacker establishes what is
  watching them. This agent announces itself in every conventional place:

      - a process named "edr-agent" in ps and /proc
      - a pinned map at the well-known path /sys/fs/bpf/edr_events
      - a write-ahead log at the predictable path /tmp/edr.wal
      - a loaded BPF program visible to bpftool prog list

  Reconnaissance costs the attacker one command and returns everything needed to
  plan around every other control in this document. Every finding below becomes
  easier once this step succeeds.

SOLUTION:
  You cannot hide from root, and attempting to is wasted effort. Invert the
  relationship instead: make reconnaissance itself the highest-fidelity
  detection. Alert on execution of bpftool, on reads of the pin path, on access
  to the WAL path, and on process-enumeration patterns targeting the agent.

  The attacker's cheapest and most reliable first action then becomes your
  strongest signal. This is a better position than invisibility, because it does
  not depend on the attacker failing to look.


================================================================================
SECTION 1 - PRESENT IN THE CODE ON DISK TODAY
================================================================================

--------------------------------------------------------------------------------
NOW-1  SYMLINK ATTACK ON /tmp/edr.wal                               [CRITICAL]
--------------------------------------------------------------------------------
ISSUE:
  The agent runs as root and opens the WAL with create(true). An attacker who
  pre-creates /tmp/edr.wal as a symlink to /etc/shadow, an authorized_keys file,
  or any other target causes the root-owned agent to append attacker-influenced
  JSON into it. This is a root-privileged arbitrary-append primitive.

SOLUTION:
  Move to /var/log/edr/ mode 0700 owned by a dedicated agent uid. Open with
  O_NOFOLLOW. Verify the inode after opening.

--------------------------------------------------------------------------------
NOW-2  PERF RING DROPS ARE DISCARDED                                    [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  read_events() returns Events { read, lost } and the code reads only .read. An
  attacker floods the host with trivial execs until the per-CPU ring overflows,
  then performs the real exec inside the dropped window. Telemetry is lost
  silently and the dashboard looks calm.

SOLUTION:
  Log and alert on lost. Enlarge the ring. Migrate to BPF RingBuf. Treat any
  nonzero loss as a detection gap, not a statistic.

--------------------------------------------------------------------------------
NOW-3  OUT-OF-BOUNDS READ ON PERF BUFFER                                [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  buf.as_ptr() is cast to *const ProcessEvent and read_unaligned() is called with
  no length check. A short or truncated perf record reads past the buffer.

SOLUTION:
  Check buf.len() >= size_of::<ProcessEvent>() before the cast.

--------------------------------------------------------------------------------
NOW-4  UNKEYED HASH CHAIN IS RECOMPUTABLE                               [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  chain_hash() is unkeyed SHA256 over public fields. There is no secret anywhere
  in the agent, and the algorithm is in the repository. A root attacker edits any
  record and recomputes every subsequent hash. Separately, deleting the last N
  records leaves a chain that verifies perfectly.

  What the chain DOES catch: disk corruption, naive edits that do not rewrite the
  chain, reordering, and deletion from the middle.

  What it does NOT catch: a root attacker who recomputes forward, or who
  truncates the tail.

SOLUTION:
  Forward-secure sealing - see Section 8. Anti-truncation via an off-box sequence
  high-water mark - also Section 8.

--------------------------------------------------------------------------------
NOW-5  DELIMITER AMBIGUITY IN THE HASH PAYLOAD                (SELF)  [MEDIUM]
--------------------------------------------------------------------------------
ISSUE:
  See CORRECTION above. An attacker-chosen binary name containing the delimiter
  makes two distinct records hash identically.

SOLUTION:
  Length-prefix the fields in both chain_hash() and verify.py.

--------------------------------------------------------------------------------
NOW-6  sudo -E PRESERVES THE ENVIRONMENT                              [MEDIUM]
--------------------------------------------------------------------------------
ISSUE:
  .cargo/config.toml sets runner = "sudo -E". LD_PRELOAD, RUSTFLAGS, or similar
  under a developer's cargo run give code execution as root.

  Second-order consequence: RUST_LOG is also attacker-controllable under a
  preserved environment, enabling log flooding and disk exhaustion via verbose
  logging alone.

SOLUTION:
  Drop -E. Use setcap cap_bpf,cap_perfmon+ep on the binary - subject to AGT-7 -
  or run from a systemd unit with an explicit, minimal environment.

--------------------------------------------------------------------------------
NOW-7  AGENT-SUPPLIED TIMESTAMP CAN BE MOVED                          [MEDIUM]
--------------------------------------------------------------------------------
ISSUE:
  Local::now() is read on a host whose clock root controls. Forensic ordering can
  be corrupted arbitrarily by changing the system clock.

SOLUTION:
  Server-side receipt time is authoritative. Use a monotonic seq for ordering.
  Flag clock skew between agent and collector.

--------------------------------------------------------------------------------
NOW-8  DELETING THE WAL PRODUCES A CLEAN CHAIN         (SELF)          [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  resume_chain() finds no file, returns GENESIS_HASH, and the agent starts a
  pristine chain. verify.py then reports a perfectly valid chain over an empty
  history. Truncation-to-zero produces a clean verification result rather than an
  alert - the strongest possible outcome for the attacker.

SOLUTION:
  The collector must reject a genesis-start from an agent it has already
  enrolled. Locally, persist chain position in a location separate from the WAL
  so that deleting one does not reset the other.

--------------------------------------------------------------------------------
NOW-9  SIGTERM IS NOT HANDLED                          (SELF)        [MEDIUM]
--------------------------------------------------------------------------------
ISSUE:
  Only signal::ctrl_c() - SIGINT - is awaited. systemd sends SIGTERM on
  systemctl stop, which bypasses the graceful shutdown path entirely. Up to 1000
  buffered events are discarded on every legitimate service stop, and an attacker
  can trigger the same loss deliberately with a single kill.

SOLUTION:
  Await SIGINT and SIGTERM together via tokio::signal::unix::signal, and run the
  same drain path for both.

--------------------------------------------------------------------------------
NOW-10  A SECOND AGENT INSTANCE CORRUPTS THE CHAIN                     [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  Two processes appending to one WAL with independent last_hash state interleave
  their records and corrupt the chain. An attacker starts a second copy
  deliberately: the integrity guarantee is destroyed, and the resulting damage is
  indistinguishable from tampering by a third party.

SOLUTION:
  Enforce single-instance operation with flock on the WAL or a pidfile. Refuse to
  start rather than degrade.

--------------------------------------------------------------------------------
NOW-11  NON-UTF-8 BINARY NAMES EVADE EVERY NAME RULE                   [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  Linux filenames permit any byte except NUL and "/". A binary named with invalid
  UTF-8 causes from_utf8().unwrap_or("<unknown>") to log it as "<unknown>". Every
  name-based rule fails, and every such process becomes indistinguishable from
  every other one. This is a free and total evasion of the highest-confidence
  detection tier.

SOLUTION:
  Hex-encode the raw bytes when UTF-8 decoding fails rather than collapsing to a
  placeholder. Treat a non-UTF-8 comm as suspicious in its own right - legitimate
  system binaries never have one.

--------------------------------------------------------------------------------
NOW-12  TIMESTAMP REFLECTS READ TIME, NOT EVENT TIME                  [MEDIUM]
--------------------------------------------------------------------------------
ISSUE:
  Distinct from NOW-7. The timestamp is taken in userspace when the consumer
  processes the record, not in the kernel when the exec occurred. Under backlog
  it reflects queue latency. An attacker who floods the pipeline shifts the
  apparent time of their own actions without touching the clock.

SOLUTION:
  Capture bpf_ktime_get_ns() inside the probe and carry it in ProcessEvent.
  Resolve to wall-clock in userspace using a single measured boot-time offset.

--------------------------------------------------------------------------------
NOW-13  CROSS-CPU EVENT ORDERING IS NONDETERMINISTIC                  [MEDIUM]
--------------------------------------------------------------------------------
ISSUE:
  Per-CPU readers feed one channel, so WAL order is arrival order, not causal
  order. Forensic reconstruction of "what happened first" is unreliable, and an
  attacker using CPU affinity can influence how their actions are sequenced
  relative to others.

SOLUTION:
  Order by the kernel timestamp from NOW-12 rather than by arrival. If ordering
  is left as-is, document the limitation - an unreliable timeline presented as
  reliable is worse than an acknowledged gap.

--------------------------------------------------------------------------------
NOW-14  WAL DISK EXHAUSTION                                            [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  The WAL grows without bound. An attacker floods execs until it exhausts the
  filesystem, causing a host outage caused by the security agent itself. This
  attacks the project's core requirement - continuous operation without impeding
  the user - rather than its security properties.

SOLUTION:
  Hard size cap with rotation. Reserved filesystem quota. Shed load loudly with a
  counted degradation marker rather than filling the disk or dying silently.


================================================================================
SECTION 2 - SENSOR / eBPF LAYER
================================================================================

--------------------------------------------------------------------------------
SEN-1  DOUBLE-FORK DEFEATS ALL PARENT-BASED RULES                      [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  An attacker double-forks to orphan the process. It reparents to init, so pcomm
  becomes "systemd" and every parent-based rule - webshell detection, database
  spawning a shell, service spawning an interpreter - silently fails. This costs
  the attacker nothing and is rarely tested for.

SOLUTION:
  Capture bpf_get_current_cgroup_id(). One helper call, survives reparenting, and
  keeps a webshell inside nginx's cgroup regardless of forking. Additionally
  maintain a userspace pid -> (ppid, comm) ancestry cache so the true chain can be
  reconstructed after the fact.

--------------------------------------------------------------------------------
SEN-2  ONLY sched_process_exec IS HOOKED                               [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  Fileless execution, in-memory payloads, injected shellcode, LD_PRELOAD hijacks,
  and pure-fork workers are all invisible. An entire class of modern technique
  produces no event at all.

SOLUTION:
  Add sensors for sched_process_exit, security_bprm_check, kernel module load,
  ptrace, the bpf() syscall, and connect/accept.

--------------------------------------------------------------------------------
SEN-3  BPF PROGRAM CAN BE DETACHED BY ROOT                             [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  bpftool prog detach stops collection and the agent never notices. The process
  remains alive and continues heartbeating while collecting nothing.

SOLUTION:
  Use bpf_link, which is harder to detach. Self-check attach state periodically.
  Include program ID and attach status in every heartbeat so the collector can
  distinguish "running" from "actually collecting".

--------------------------------------------------------------------------------
SEN-4  comm TRUNCATED AT 15 BYTES                                    [MEDIUM]
--------------------------------------------------------------------------------
ISSUE:
  A binary named systemd-journaldX displays as systemd-journal. Free masquerade
  against any name-based rule.

SOLUTION:
  Capture the filename field from the tracepoint for the full path. It is already
  present in the tracepoint buffer at no additional kernel cost.

--------------------------------------------------------------------------------
SEN-5  TOCTOU ON BINARY IDENTITY                                     [MEDIUM]
--------------------------------------------------------------------------------
ISSUE:
  The binary can be replaced or renamed after exec; the logged path no longer
  identifies the content that actually ran.

SOLUTION:
  Record dev + inode + mtime alongside the path. Hash the binary if the
  performance budget allows.

--------------------------------------------------------------------------------
SEN-6  PINNED MAP PERMITS EVENT INJECTION                           [CRITICAL]
--------------------------------------------------------------------------------
ISSUE:
  /sys/fs/bpf/edr_events may be readable, writable, or deletable by others
  depending on bpffs mount options. The severe case is not disclosure but write:
  anyone with CAP_BPF can inject fabricated events directly into the agent's read
  path, which the agent then hashes and seals as genuine. This yields arbitrary
  forged records inside the tamper-evident log, signed by the defender.

SOLUTION:
  0600 pin inside a restricted bpffs subdirectory with restrictive mount options.
  Validate event plausibility on read - a pid the agent has never seen created,
  or a field outside expected bounds, should be flagged rather than sealed.

--------------------------------------------------------------------------------
SEN-7  RAW vmlinux.rs OFFSETS VS KERNEL DRIFT                        [MEDIUM]
--------------------------------------------------------------------------------
ISSUE:
  Without CO-RE relocations, a kernel layout change produces garbage ppid and
  pcomm values, causing silent misattribution rather than a visible failure.

SOLUTION:
  Use CO-RE relocations. Validate at load. Fail closed on mismatch rather than
  reporting confident nonsense.

--------------------------------------------------------------------------------
SEN-8  KERNEL ROOTKIT UNHOOKS THE TRACEPOINT                            [LOW]
--------------------------------------------------------------------------------
ISSUE:
  An attacker at kernel level removes or neuters the probe entirely. Realistically
  outside the project's threat model, but it should be named rather than ignored.

SOLUTION:
  Secure Boot, kernel lockdown, module signing, IMA. These are host-platform
  controls, not agent controls.

--------------------------------------------------------------------------------
SEN-9  PID REUSE POISONS THE ANCESTRY CACHE                            [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  An attacker forces PID wraparound by spawning through pid_max. A recycled PID
  then collides with a stale entry in the planned pid -> uid/ppid cache, and the
  agent attributes the malicious process to a benign parent. Cache poisoning by
  exhaustion, requiring no privileges beyond the ability to spawn processes.

SOLUTION:
  Key the cache on (pid, start_time) read from task_struct rather than pid alone.
  Evict on sched_process_exit so stale entries do not survive to be collided with.

--------------------------------------------------------------------------------
SEN-10  ANCESTRY CACHE IS COLD AT STARTUP                            [MEDIUM]
--------------------------------------------------------------------------------
ISSUE:
  Processes that predate the agent have no cache entry, so ancestry
  reconstruction silently returns nothing for them. An attacker with any boot
  persistence automatically satisfies this condition without effort.

SOLUTION:
  Prime the cache from /proc at startup. Mark entries recovered this way as
  lower-confidence, since they were not observed directly.


================================================================================
SECTION 3 - AGENT PROCESS
================================================================================

--------------------------------------------------------------------------------
AGT-1  AGENT CAN BE SIGKILLED                                          [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  A single kill stops all collection. Nothing restarts it and nothing off-box
  necessarily notices.

SOLUTION:
  systemd Restart=always. Heartbeat so the collector observes the death. A BPF
  LSM task_kill hook denying signals to the agent pid - this is the eBPF-native
  answer and a strong result for the project.

--------------------------------------------------------------------------------
AGT-2  AGENT RUNS AS FULL ROOT                                         [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  Compromise of the agent is compromise of the host. The blast radius of any
  memory-safety bug - see NOW-3 - is maximal.

SOLUTION:
  Drop to CAP_BPF + CAP_PERFMON after load, then drop privileges. Apply a seccomp
  filter. Split the privileged loader from the unprivileged shipper process.

--------------------------------------------------------------------------------
AGT-3  DETECTION RULES LIVE IN THE AGENT BINARY                        [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  A root attacker reads the binary and learns the complete detection logic, then
  operates around it. Every rule you ship is a rule they can enumerate.

SOLUTION:
  Run a second scoring pass server-side using rules the agent never contains.
  Note the genuine tension: this conflicts with bandwidth-minimising designs that
  ship only alerts. Enough raw context must reach the collector for off-box
  scoring to be possible at all.

--------------------------------------------------------------------------------
AGT-4  CHANNEL BACKPRESSURE UNDER FLOOD                              [MEDIUM]
--------------------------------------------------------------------------------
ISSUE:
  The bounded mpsc channel stalls sensor tasks under load, which in turn fills the
  perf ring and triggers the loss described in NOW-2.

SOLUTION:
  Count and alert on drops. Degrade loudly, never silently.

--------------------------------------------------------------------------------
AGT-5  UNBOUNDED pid CACHE GROWTH                                    [MEDIUM]
--------------------------------------------------------------------------------
ISSUE:
  Memory exhaustion against the agent, and through it against the host.

SOLUTION:
  LRU with a hard cap. Evict on sched_process_exit.

--------------------------------------------------------------------------------
AGT-6  AGENT BINARY, CONFIG, AND UNIT FILE PERMISSIONS                 [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  All three are executed or read by a root process. If packaging leaves any of
  them group- or world-writable, any local user escalates to root by editing
  them. The security agent becomes the privilege escalation path.

SOLUTION:
  Binary root-owned 0755 or stricter, config 0600, unit file 0644 root-owned, and
  every parent directory non-writable by non-root. Verify at install and, if
  practical, at startup.

--------------------------------------------------------------------------------
AGT-7  setcap MAKES THE BINARY A CAPABILITY-BEARING TARGET           [MEDIUM]
--------------------------------------------------------------------------------
ISSUE:
  The remediation recommended in NOW-6 and AGT-2 - setcap cap_bpf,cap_perfmon+ep
  - creates its own exposure. Any user permitted to execute that binary invokes
  it with those capabilities.

SOLUTION:
  Restrict execute permission to root or a dedicated group alongside the setcap.
  A capability grant without a corresponding execute restriction is a net loss.

--------------------------------------------------------------------------------
AGT-8  SELF-TRIGGERING IF THE AGENT EVER EXECS                       [MEDIUM]
--------------------------------------------------------------------------------
ISSUE:
  Not present today, but a hard design constraint going forward. If the agent or
  its shipper ever spawns a subprocess - calling curl, invoking a helper for
  enrichment - it logs its own exec and feeds itself, producing a loop bounded
  only by the channel.

SOLUTION:
  Never spawn subprocesses from the agent; use in-process libraries. If a
  subprocess is unavoidable, filter the agent's own pid tree in the probe.


================================================================================
SECTION 4 - AGENT TO PROXY TRANSPORT
================================================================================

--------------------------------------------------------------------------------
NET-1  NO TLS OR UNVALIDATED CERTIFICATES                           [CRITICAL]
--------------------------------------------------------------------------------
ISSUE:
  Passive interception, active modification, and injection of fabricated events
  anywhere on the path.

SOLUTION:
  mTLS with a pinned CA. Do not use the system trust store, which root can add to.

--------------------------------------------------------------------------------
NET-2  DNS OR /etc/hosts HIJACK REDIRECTS THE AGENT                    [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  Root edits /etc/hosts and points the agent at an attacker-controlled collector,
  which then silently accepts and discards everything.

SOLUTION:
  Certificate pinning. The agent refuses any peer that does not present the
  expected certificate, regardless of what name resolution returns.

--------------------------------------------------------------------------------
NET-3  BEARER TOKEN STOLEN FROM DISK                                   [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  Root reads the token and impersonates the agent, injecting fabricated events or
  flooding the collector under a trusted identity.

SOLUTION:
  mTLS with a TPM-sealed client key. Scope each credential so an agent can only
  write its own stream and never another host's.

--------------------------------------------------------------------------------
NET-4  REPLAY OF CAPTURED BATCHES                                    [MEDIUM]
--------------------------------------------------------------------------------
ISSUE:
  A root attacker replays previously valid batches to duplicate or confuse the
  record, without needing to forge anything.

SOLUTION:
  Server-side deduplication on (agent_id, seq). Per-batch nonce.

--------------------------------------------------------------------------------
NET-5  FLOODING TO BURY REAL ALERTS                                  [MEDIUM]
--------------------------------------------------------------------------------
ISSUE:
  Volume as concealment - the real alert is present but drowned.

SOLUTION:
  Per-agent rate limits and quotas. Alert on volume anomalies as a signal in
  their own right. See also STO-7 for the human-facing variant.

--------------------------------------------------------------------------------
NET-6  TRAFFIC ANALYSIS                                                 [LOW]
--------------------------------------------------------------------------------
ISSUE:
  If the agent ships only when something is suspicious, the mere existence of a
  packet tells a watching attacker they were detected.

SOLUTION:
  Fixed-size, fixed-cadence heartbeats. Pad batches to uniform size.


================================================================================
SECTION 5 - THE PROXY
================================================================================
This is the component that most changes the threat model.

--------------------------------------------------------------------------------
PRX-1  PROXY COMPROMISE EQUALS FLEET-WIDE LOG FORGERY               [CRITICAL]
--------------------------------------------------------------------------------
ISSUE:
  If TLS terminates at the proxy, it can read, drop, alter, and inject events for
  every host in the fleet. One compromise defeats every agent simultaneously.

SOLUTION:
  The MAC must be computed by the agent using a key the proxy does not have, and
  verified at offshore storage. The proxy then becomes a dumb pipe that is
  structurally incapable of forging. This is the single most important design
  decision in the architecture.

--------------------------------------------------------------------------------
PRX-2  PROXY HOLDS STORAGE CREDENTIALS - PIVOT TO THE ARCHIVE       [CRITICAL]
--------------------------------------------------------------------------------
ISSUE:
  Compromising the proxy yields the credentials that reach the evidence archive.

SOLUTION:
  Append-only, write-only credentials at the proxy. No read, no delete, no list.

--------------------------------------------------------------------------------
PRX-3  PROXY READS EVENT CONTENTS                                      [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  A privacy exposure and a reconnaissance win - the proxy learns the entire
  detection posture of the fleet, including which hosts are alerting and on what.

SOLUTION:
  End-to-end encrypt payloads to the storage tier's key. The proxy sees routing
  metadata only. Prefer TCP or SNI passthrough over termination.

--------------------------------------------------------------------------------
PRX-4  EVENTS BUFFERED ON THE PROXY ARE TAMPERED WITH                  [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  Records queued on the proxy sit at rest in a location the agent no longer
  controls and the storage tier does not yet.

SOLUTION:
  The same end-to-end MAC as PRX-1. Tampering is then detected at storage rather
  than trusted at the proxy.

--------------------------------------------------------------------------------
PRX-5  SINGLE POINT OF FAILURE                                         [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  Kill the proxy and the entire fleet goes dark at once.

SOLUTION:
  Multiple proxies with agent-side failover. Agents buffer locally - the WAL
  already does this. Critically, absence of agent traffic must alert at the
  storage tier, not at the proxy, or the alerting dies with the component.

--------------------------------------------------------------------------------
PRX-6  VULNERABLE PARSER ON A LISTENING SERVICE                        [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  The proxy accepts untrusted input from every monitored host. A parser bug is
  remote code execution reachable from any compromised agent.

SOLUTION:
  Memory-safe implementation. Authenticate before parsing any untrusted body.
  Keep the surface minimal. Fuzz it. If compression is added, bound the
  decompressed size to prevent decompression bombs.

--------------------------------------------------------------------------------
PRX-7  ONE COMPROMISED AGENT DENIES SERVICE TO THE FLEET             [MEDIUM]
--------------------------------------------------------------------------------
ISSUE:
  A single flooding host starves every other host's telemetry.

SOLUTION:
  Per-agent quotas and fair queuing.


================================================================================
SECTION 6 - OFFSHORE STORAGE AND ANALYST TOOLING
================================================================================

--------------------------------------------------------------------------------
STO-1  ATTACKER REACHING STORAGE DELETES THE EVIDENCE               [CRITICAL]
--------------------------------------------------------------------------------
ISSUE:
  The archive is the last copy. Deletion there is unrecoverable.

SOLUTION:
  WORM storage. S3 Object Lock in compliance mode, versioning, MFA delete, and a
  separate cloud account under a separate identity.

--------------------------------------------------------------------------------
STO-2  NO SERVER-SIDE VERIFICATION                                  [CRITICAL]
--------------------------------------------------------------------------------
ISSUE:
  If MACs are only ever checked by the agent that produced them, verification is
  circular and therefore meaningless.

SOLUTION:
  Recompute every MAC on ingest. Quarantine and alert on failure rather than
  storing and trusting.

--------------------------------------------------------------------------------
STO-3  STORED XSS FROM ATTACKER-CONTROLLED PROCESS NAMES               [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  comm is chosen by the attacker and will be rendered in the dashboard. A binary
  named with an HTML payload becomes stored XSS against the analyst - the agent
  becomes the delivery mechanism.

SOLUTION:
  Context-aware escaping. Strict CSP. Never assign to innerHTML.

--------------------------------------------------------------------------------
STO-4  SILENT GAPS ARE NEVER NOTICED                                   [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  Missing telemetry looks identical to a quiet host.

SOLUTION:
  Per-agent sequence high-water mark. Alert on regression, on gaps, and on a
  stalled counter while heartbeats continue.

--------------------------------------------------------------------------------
STO-5  CROSS-BORDER DATA HANDLING                                    [MEDIUM]
--------------------------------------------------------------------------------
ISSUE:
  Process names, usernames, and hostnames are arguably personal data, and
  "offshore" invites the question in any review.

SOLUTION:
  Encryption at rest, a data processing agreement, and a documented residency
  review.

--------------------------------------------------------------------------------
STO-6  CSV FORMULA INJECTION INTO THE ANALYST WORKSTATION              [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  A binary named =cmd|'/c calc'!A1 becomes code execution on the analyst's
  machine the moment events are exported and opened in a spreadsheet. STO-3
  covers the browser; this covers the spreadsheet, which is where security teams
  actually work. The payload travels the full length of your trusted pipeline.

SOLUTION:
  Prefix exported cells with a single quote, or reject values with a leading
  = + - @ character. Apply at export, not at ingest, so the raw record stays
  faithful.

--------------------------------------------------------------------------------
STO-7  ALERT FATIGUE AS A DELIBERATE TECHNIQUE                       [MEDIUM]
--------------------------------------------------------------------------------
ISSUE:
  Distinct from bandwidth flooding. The attacker generates hundreds of plausible
  medium-severity alerts so the real one is triaged as noise. The target is the
  human, and no technical control on the pipeline addresses it.

SOLUTION:
  Deduplicate and cluster related events. Rate-limit per rule. Score a burst as a
  single incident rather than as many findings. Surface "unusual alert volume"
  as its own high-severity signal.


================================================================================
SECTION 7 - SUPPLY CHAIN AND BUILD
================================================================================

--------------------------------------------------------------------------------
SUP-1  PATH HIJACK VIA which("bpf-linker")                             [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  build.rs shells out to cargo build and resolves bpf-linker from PATH. This is
  code execution on any developer or CI machine that builds the project.

SOLUTION:
  Pin the toolchain. Use absolute paths. Build in a clean, isolated CI
  environment.

--------------------------------------------------------------------------------
SUP-2  AGENT BINARY REPLACED WITH A STUB                               [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  A replacement that heartbeats but never reports leaves the fleet view green
  while the host is entirely unmonitored - the ideal outcome for an attacker.

SOLUTION:
  Sign the binary. Use IMA/EVM or dm-verity. Have the agent attest its own build
  hash at enrollment and have the collector pin it.

--------------------------------------------------------------------------------
SUP-3  SHARED FLEET-WIDE BOOTSTRAP SECRET                              [HIGH]
--------------------------------------------------------------------------------
ISSUE:
  One host compromise enrolls unlimited fake agents, which can then flood, forge,
  or dilute the fleet's telemetry.

SOLUTION:
  Per-host, short-lived enrollment tokens. TPM-based attestation.

--------------------------------------------------------------------------------
SUP-4  MALICIOUS DEPENDENCY UPDATE                                   [MEDIUM]
--------------------------------------------------------------------------------
ISSUE:
  A compromised crate executes with the agent's privileges, which are root.

SOLUTION:
  cargo audit and cargo vet in CI. Lockfile committed - it is. Vendor
  dependencies for release builds.

--------------------------------------------------------------------------------
SUP-5  BUILD-TIME TOCTOU ON THE BPF OBJECT                           [MEDIUM]
--------------------------------------------------------------------------------
ISSUE:
  build.rs compiles the eBPF program into target/, copies it to OUT_DIR, and the
  agent embeds it. If target/ is writable by another user, the object can be
  swapped between compilation and embedding, placing attacker-controlled bytecode
  inside a signed agent.

SOLUTION:
  Build in a private directory with restrictive permissions. Verify a hash of the
  object between compile and embed.

SECTION 8 - THE OFFLINE TAMPERING PROBLEM
================================================================================
Raised in review: if the network is cut, logs sit locally and can be tampered
with before transmission. This is the correct question to ask, and the current
hash chain does not answer it - see NOW-4.

--------------------------------------------------------------------------------
FORWARD-SECURE SEALING
--------------------------------------------------------------------------------
  Reference: Schneier and Kelsey, 1998, "Cryptographic Support for Secure Logs on
  Untrusted Machines." Deployed today as systemd-journald Forward Secure Sealing
  (journalctl --setup-keys).

  At enrollment the server generates K0 and provisions it to the agent.
  For each record i:

      MAC_i   = HMAC(K_i, record_i || MAC_{i-1})
      K_{i+1} = H(K_i)              <- evolve
      erase K_i                     <- the critical step

  Key evolution is one-way. When the attacker compromises the host at record t
  they obtain K_t and nothing earlier, because K_0 through K_{t-1} are destroyed
  and cannot be derived from K_t.

  PROPERTY: every record written before the compromise is unforgeable, even by
  root. They cannot modify it, recompute it, or fabricate a replacement. They can
  forge records from t onward - unavoidable, they own the machine - but the
  evidence of how they got in is already sealed.

  CAVEATS:
    - Erasure must be real. Journaling and copy-on-write filesystems may leave
      old key material recoverable. Keep the evolving key in memory, persist only
      under explicit sync to a dedicated location, or seal it to a TPM.
    - Evolve on a time schedule, not only per record. Otherwise an attacker
      landing during an idle period finds a key still valid for records they wish
      to backdate. journald uses time epochs for exactly this reason.

--------------------------------------------------------------------------------
ANTI-TRUNCATION
--------------------------------------------------------------------------------
  Forward security seals content but does nothing about deletion. That requires
  external state the attacker cannot reach.

    - Add a monotonic seq to every record, inside the MAC'd payload.
    - The server persists the highest seq and MAC ever received per agent.
    - On reconnect, the agent's claimed position is checked against that
      high-water mark. A regression is proof of rollback.
    - Frequent checkpoints while online bound how much is ever at risk.
    - The server must additionally reject a genesis-start from a known agent -
      see NOW-8, without which deletion of the entire WAL passes verification.

  This is why the collector must run on a different machine than the agent. A
  collector on the same VM anchors nothing.

--------------------------------------------------------------------------------
SILENCE IS A SIGNAL
--------------------------------------------------------------------------------
  This is the strongest argument available, because it turns the scenario against
  the attacker. To tamper with local logs they must first cut the network. But
  the collector sees heartbeats, so network loss is itself an alert:

      1. Cut the network      -> collector alerts immediately
      2. Tamper with the WAL  -> pre-compromise records are sealed
      3. Reconnect            -> seq high-water check flags truncation

  They cannot perform step 2 quietly. The offline window is the only vulnerable
  surface, and entering it is loud.

--------------------------------------------------------------------------------
LOCAL HARDENING (raises the bar, does not close it)
--------------------------------------------------------------------------------
  Each of these has the useful property that defeating it generates an exec event
  the agent itself detects.

    - Move the WAL out of /tmp. Use /var/log/edr/ mode 0600, dedicated uid.
    - chattr +a (append-only). Removing it requires CAP_LINUX_IMMUTABLE, and
      chattr is already on the anti-forensics detection list.
    - SELinux or AppArmor policy restricting WAL writes to the agent binary alone.
    - Killing the agent requires an exec, which is detectable right up until it
      succeeds.

--------------------------------------------------------------------------------
WHAT REMAINS UNSOLVABLE
--------------------------------------------------------------------------------
  You cannot make data on a machine tamper-proof when the adversary has root on
  that machine. You can only:

      1. Make pre-compromise records unforgeable    (forward-secure sealing)
      2. Make deletion detectable                   (off-box high-water mark)
      3. Bound the window                           (ship continuously)
      4. Make entering that window noisy            (heartbeat + silence alerting)

  Commercial EDR products face this identically and answer it the same way, plus
  kernel-level self-protection to make killing the agent harder. None of them
  claim offline logs are unforgeable against root.

--------------------------------------------------------------------------------
STATEMENT FOR REVIEWERS
--------------------------------------------------------------------------------
  "Our chain detects modification and reordering, but an unkeyed chain is
   recomputable by a root attacker, so it does not survive that threat model on
   its own. We address it with forward-secure sealing - HMAC with an evolving,
   erased key - which makes every record written before compromise unforgeable
   even to an attacker who owns the machine. Truncation is caught by an off-box
   sequence high-water mark, and the offline window required to attempt any of
   this is itself alerted on via heartbeat loss."

SECTION 11 - REMEDIATION ORDER
================================================================================

FIX FIRST
  1. NOW-1  - the /tmp symlink issue. A root-privileged arbitrary-append
              primitive present in the code right now, and a ten-line fix.
  2. PRX-1  - end-to-end MAC the proxy cannot compute. The architectural decision
              that makes the proxy safe to exist at all. Everything else about
              the proxy is mitigation; this is prevention.
  3. NOW-2  - the lost counter. Until it exists you cannot distinguish a quiet
              host from one actively evading you, which undermines every other
              control here.
  4. SEN-6  - the pinned map write path. Forged records inside a tamper-evident
              log defeat the entire integrity story, and the fix is a permission
              change.

THEN
  5. NOW-8, NOW-9, NOW-10 - the three defects in the review-period code. Each is
     small, and NOW-8 in particular silently negates the chain.
  6. NOW-3 bounds check, NOW-5 length-prefixed hashing, NOW-6 sudo -E.
  7. NOW-11 non-UTF-8 handling, SEN-1 cgroup id, SEN-4 filename capture. Together
     these restore the parent-based detections that double-forking, renaming, and
     invalid UTF-8 currently defeat for free.
  8. NOW-12 kernel timestamps, NOW-14 WAL size cap.
  9. Section 8 forward-secure sealing plus sequence numbers and heartbeats.
 10. AGT-2 privilege dropping, AGT-1 restart supervision, AGT-6 file permissions.
 11. Storage immutability (STO-1), server-side verification (STO-2), and output
     encoding for both the dashboard (STO-3) and CSV export (STO-6).

POINTS WORTH RAISING EXPLICITLY IN REVIEW
  - DISC-1 reframes the whole problem. You cannot hide from root, so make
    reconnaissance the detection instead of trying to prevent it.
  - SEN-1 matters more than it appears. Double-forking defeats the entire
    parent-based ruleset for free, and it is rarely tested.
  - AGT-3 is in genuine tension with any design that ships only alerts to save
    bandwidth. A root attacker reads the detection logic out of the binary, so
    some scoring must live where they cannot see it.
  - NOW-8 is the clearest example of why threat modelling must cover remediation
    code as well as original code. The fix for one truncation problem introduced
    a cleaner one.

SECTION 12 - LIMITS OF THIS DOCUMENT
================================================================================
This list is not exhaustive, and no threat model is. What it represents is two
structured passes - one by component, one by attacker objective - over a
codebase of roughly four hundred lines of hand-written source, performed by
reading rather than by execution.

SPECIFIC LIMITS
  - No finding here was confirmed by running anything. The agent does not build
    or run on the review machine, so every code-level finding is a static read.
  - The proxy and collector do not exist as code yet. Sections 5 and 6 model a
    design, not an implementation. Parsers and authentication flows are where
    most real vulnerabilities live, and neither has been written.
  - No fuzzing, no dynamic analysis, no adversarial testing against a running
    agent has been performed.
  - Kernel-level attacks (SEN-8) are named but not explored in depth.
  - The detection rules themselves have not been evaluated for false-negative
    rate against real attack tooling.

RECOMMENDED NEXT STEPS BEYOND THIS DOCUMENT
  - Run cargo clippy and cargo audit on the Linux target.
  - Fuzz the collector's parser once it exists.
  - Test the evasions in Section 9 against a running agent and record which ones
    actually work. Assume some will behave differently in practice than on paper.
  - Have someone who did not write the agent perform an independent pass. Two
    passes by the same reviewer share the same blind spots.
