Sealing the Chain

Turning a process-execution monitor with a decorative hash chain into one whose logs a root-level attacker cannot silently rewrite.

Project

AbstractWhat this report covers

The project is a lightweight endpoint agent that watches every process execution on a Linux host from inside the kernel and writes a tamper-evident log. The baseline implementation had the right architecture and a hash chain that did not work: it was unkeyed, so the attacker it was meant to catch could recompute it, and it covered only half the fields in each record — including neither the severity nor the parent process.

This report describes the system, audits that baseline, and documents the remediation: forward-secure sealing under an evolving key, a length-prefixed payload covering every field, sequence numbering, and a new off-box collector that supplies the one thing an on-host log structurally cannot — an outside witness to how many records should exist. Sixty-one findings are tracked; thirty are closed in code. Three of them are defects in the code written during this work, found by reviewing it against its own threat model, and are reported alongside the rest.

Section 1What the system is

An EDR agent — endpoint detection and response — is a background process that records security-relevant activity on a machine so that an intrusion can be detected while it happens and reconstructed afterwards. This one has a deliberately narrow remit: it records process executions, and it tries very hard to make that record hard to falsify.

1.1How it sees executions

The agent attaches a small program to the kernel's sched:sched_process_exec tracepoint using eBPF, a mechanism that lets user-supplied code run inside the kernel under a static verifier that proves it cannot crash or loop forever. Every time any process on the host calls execve, that program runs, captures a fixed-size record, and pushes it through a per-CPU ring buffer to the userspace agent.

This is why the agent can be cheap. It is not polling /proc, not scanning the filesystem, and not sitting in the path of any syscall it does not care about. It is idle until an exec happens, and an exec costs it a few hundred nanoseconds in the kernel plus a memory copy.

The workspace is four Rust crates: edr-agent-ebpf (the kernel probe, no_std), edr-agent (the userspace daemon), edr-agent-common (the shared kernel↔userspace ABI), and — new in this work — edr-collector.

1.2Why the log needs to be sealed

The threat that shapes the whole design is an attacker who gets root on the monitored host. That is not an edge case; it is the normal outcome of the intrusions this agent exists to record. Once they have root, they can read the log file, edit it, and delete the lines describing how they got in.

Nothing on the host can prevent that. The design goal is therefore weaker and achievable: make the tampering evident. Each record is chained to the one before it, so that altering any record invalidates every record after it, and doing so undetectably requires something the attacker does not have.

That last clause is where the baseline failed.

Section 2The baseline, as audited

At commit 20b75fe the project was about 306 lines of hand-written code across four files. It worked: it loaded the probe, caught execs, scored them, and appended JSON records to a write-ahead log. The architecture was sound. The integrity mechanism was not.

2.1The chain was unkeyed

SHA-256 is a public function. There is no secret in that expression. An attacker who edits a record can recompute its hash, then recompute every subsequent hash in the file, and the result verifies perfectly. The chain detected accidental corruption — a bad disk, a truncated write — and nothing else. Against the adversary in the threat model it was decoration.

2.2The chain covered half the record

A second, independent flaw. The log record had eight content fields. The hash covered four of them.

Field in AgentLogCovered by the hashConsequence if not
timestampYes—

pidYes—
process_nameYes—
severityNoRewrite CRITICAL → INFO; chain still verifies
event_typeNoReclassify the event entirely
ppidNoErase the parent link — the attack chain
parent_process_nameNoRewrite lineage: make a shell look like it came from systemd

This is worse than it first appears. Even had the hash been keyed, an attacker could have downgraded every CRITICAL record to INFO and severed every parent-child link in the log without touching a single byte the hash was computed over. The fields that carry the meaning of an alert were precisely the fields left outside the seal.

2.3The concatenation was ambiguous

The five values were joined with no delimiter at all. process_name is chosen by the attacker — it is the name of a binary they can create. Two different records could therefore be made to hash identically by shifting characters across the implicit field boundary, letting one record be substituted for another.

2.4Deletion was free

Records had no sequence number. A hash chain proves that the records you are holding are in order and unmodified. It says nothing about records that are no longer there. Deleting the last N lines of the log leaves a chain that verifies perfectly — and the last N lines are exactly the ones an attacker wants gone.

2.5Six further defects in the same file

  • The log lived in /tmp. A world-writable directory. Any unprivileged user could pre-create /tmp/edr.wal as a symlink and have the root-run agent write through it to a file of their choosing.
  • Crash recovery recovered nothing. The routine that ran on startup printed "Data verified. Cleaning up old pin" and then deleted the pinned kernel map. It read nothing. The comment on the line where the reading should have happened said // In the future: Load map here to read missed events. The pinned map is the mechanism that holds events buffered across an agent restart, and startup destroyed it.
  • A panic on read. read_events(&mut buffers).await.unwrap() — a transient error in the perf ring terminated the agent.
  • An out-of-bounds read. The perf record was cast to ProcessEvent via read_unaligned with no check that the buffer was large enough to hold one.
  • No rotation. The log grew without bound until the partition filled — a denial of service the attacker triggers by making noise.
  • Nothing left the host. The comment read // B. Send to Network (Stdout for now). Every record, including the sealed ones, stayed on the machine the attacker controlled.

Section 4Change one: forward-secure sealing

The central fix. An unkeyed hash cannot resist an attacker with root, and neither can a keyed hash whose key is sitting on the same disk — they simply read the key and re-sign. The resolution is to make the key change over time and destroy its own past, a construction due to Schneier and Kelsey and used by systemd's journal.

4.1The construction

A 32-byte root key K₀ is generated on first start and printed once, for the operator to copy off the machine. Thereafter:

  • Each record is sealed with HMAC-SHA256 under the current epoch key, over the record's fields concatenated with the previous record's MAC.
  • Every 60 seconds the key advances: K(n+1) = SHA256(K(n)), and K(n) is overwritten in memory and on disk.

Because SHA-256 is one-way, K(e) yields nothing about K(e−1). The property this buys is precise, and worth stating precisely: an attacker who compromises the host at time T can forge records after T, but cannot forge or alter records written before T without the alteration being detectable by anyone holding K₀ off-box. It does not stop them from lying about the future. It stops them from editing the evidence of how they arrived.

4.2Closing the payload

Two changes to what gets sealed, both narrow and both necessary:

The record format now lives in one module shared by the agent, the collector and the Python verifier, rather than being written out three times. Drift between those copies would silently break every verification, which is the kind of bug that is found years later by an investigator who needed it to work.

Section 5Change two: the collector

Sealing solves forgery. It does not solve deletion, and no on-host mechanism can. A log that has had its tail removed is indistinguishable from a log that was never longer — the surviving records are genuine, correctly sealed, and in order. Detecting the removal requires knowing how many records there should have been, and that knowledge has to live somewhere the attacker does not control.

edr-collector is a new 992-line crate that provides it: an HTTP service, deployed off the monitored host, that verifies and stores what agents send.

Silence deserves emphasis. It is the loudest signal the system has, and it is inaudible from the host — an agent that has been killed cannot report that it was killed. Only an observer expecting traffic can notice its absence.

5.2The agent side

edr-agent/src/shipper.rs (366 lines) reads the write-ahead log rather than tapping the event channel. That is deliberate: shipping from the WAL means a record is durable before it is transmitted, and a crash mid-send loses nothing. Position is tracked as (inode, byte offset, acked_seq); the inode comparison is what detects log rotation.

Catch-up is rate-limited to roughly 100 records per second by default. After a long outage the backlog can be large, and an unthrottled drain would saturate the uplink and spike CPU at precisely the moment somebody is already looking at the host.

Two exposures the collector creates

Reported rather than glossed. First, the collector holds every enrolled host's K₀ — compromising it grants the ability to forge any host's entire history retroactively, which is strictly more power than compromising any single agent. It must be watched more closely than the hosts it collects from. Second, the workspace builds release with panic = "abort", and the collector parses attacker-influenced JSON on a network-facing path; one panic in a request handler blinds every enrolled host at once.

Section 6Change three: sensor and runtime

6.1What the probe now captures

The kernel record grew from 5 fields to 9, each addressing a specific evasion:

AddedEvasion it answersFinding

6.2Runtime robustness

  • The log moved to /var/log/edr, mode 0700, opened with O_NOFOLLOW and checked for symlinks, directory type, permissions and hardlinks before any write. NOW-1
  • Perf ring headroom raised from 2 pages to 16 — 8 KB to 64 KB per CPU, roughly 40 to 340 events of burst capacity, at a cost of about 1 MB of RSS on a 16-core host. The lost counter is now surfaced and alerted, but the counter only tells you drops happened; the headroom is what stops a noisy exec burst from causing them. Inducing drops is cheap for an attacker and dropping events is what they want. NOW-2
  • Bounds check before the cast, replacing the out-of-bounds read. NOW-3
  • SIGTERM handled alongside SIGINT, so a normal systemctl stop flushes rather than truncating. NOW-9
  • flock on the log — a second instance refuses to start instead of interleaving two chains into one file. NOW-10
  • 256 MB cap with one-generation rotation, replacing unbounded growth. NOW-14
  • Non-blocking send with a counted drop, replacing a blocking send that applied backpressure into the kernel read loop. AGT-4
  • Read-side plausibility validation — events with impossible PIDs, zero or future kernel timestamps, empty comm, or non-zero reserved padding are rejected and counted. This makes sloppy injection into the pinned map noisy. It does not defeat careful injection, and SEN-6 remains open.

6.3Detection scoring

One change of posture rather than of code. Reconnaissance and anti-forensics tooling — bpftool, chattr, shred, auditctl — now scores CRITICAL. An attacker enumerating the monitoring before disabling it is not noise to be filtered; it is one of the highest-signal events the agent will ever see. DISC-1

Section 7Reviewing the new code against its own model

The collector was then audited the same way the original agent had been. Three defects were found in code written during this work. They are reported here for the same reason they are in the threat model: a review that exempts its own output is not a review.

7.1High  COL-1 — unbounded key derivation from unverified input

The epoch field selects which key verifies a record. It therefore cannot itself be verified first — that is a property of the construction, not an oversight. It was then used directly as a loop count, one SHA-256 per iteration.

A single HTTP POST carrying epoch = 2⁶⁴−1 spins inside the request handler while holding the mutex every other host needs. No forgery, no credentials, no access to any agent: one request blinds the entire fleet, and unlike a panic it never recovers.

Fixed by capping derivation at MAX_EPOCH_WALK — about two years of continuous agent uptime — and refusing anything beyond as an anomaly rather than computing it. The same constant was added to verify.py, because the offline verifier is what an investigator runs against exactly the file an attacker just wrote; hanging the verifier stops an investigation as effectively as deleting the records.

7.2Medium  COL-2 — a storage failure destroyed the batch it failed on

In-memory state advanced per record as a batch was processed. If the append to disk then failed, the handler returned without rolling back, so the agent's retry hit the "already seen this sequence" branch and the batch was discarded permanently. One transient ENOSPC silently destroyed telemetry both sides believed was safe. The acknowledgement returned on that path was also computed as high_seq − accepted, which is wrong whenever sequence numbers are not dense — it could acknowledge records that were never written.

Fixed by snapshotting state before the batch, restoring it on write failure, and acknowledging the snapshot's high-water mark.

7.3Low  COL-3 — the verifier aborted instead of reporting

A non-numeric seq or epoch in a tampered log reached a comparison in verify.py and raised TypeError, ending the run with a traceback at the first bad record rather than an alert. An attacker who cannot forge a record could still make the verifier fall over. Fixed by type- and range-checking both fields and reporting the failure like any other integrity violation.

The generalisation

A value taken from unverified input and used as a loop count, an allocation size, or an index is a denial of service until it is bounded. Rust's type system caught the parsing half for free — serde_json into a u64 rejects a string or a negative — but not the range half, and the Python verifier of the same format had neither.

8.1What the system now resists

  • Editing any field of any record written before the compromise, undetectably.
  • Deleting records, including the tail, without a visible sequence gap off-box.
  • Wiping the log and state to mint a clean history under a fresh key.
  • Renaming a binary to hide behind comm's 15-character truncation.
  • Double-forking to sever the parent link.
  • A hostile TLS-terminating proxy reading, forging or replaying batches.
  • Killing the agent and having the host read as merely quiet.
  • Replacing the binary with a stub that heartbeats convincingly.

8.2What it does not

  • Anything that never calls execve. Only sched_process_exec is hooked. Code injected into a running process, an interpreter loading a payload from a socket, a library forced in via LD_PRELOAD — all invisible. This is the largest coverage gap in the system. SEN-2
  • Careful injection into the pinned map. Plausibility checks catch sloppy forgery. An attacker who reads the probe source can craft values that pass. SEN-6
  • Forging records after the compromise. Inherent to forward-secure sealing and not a defect: the attacker holds the current key. Only the past is protected.
  • Running on a kernel other than the one it was built against. No CO-RE relocations; vmlinux.rs offsets are fixed at build time, and wrong offsets produce confident nonsense rather than an error. SEN-7
  • A kernel rootkit. Below the agent's vantage point entirely; this is Secure Boot, lockdown and module signing territory. SEN-8
  • Privilege separation. The agent still runs as root. systemd hardening bounds the blast radius; it does not remove the condition. AGT-2

Section 9Verification status

Read this before relying on any of the above

None of this code has been compiled or executed. The agent is Linux-only and does not build on the machine the review was performed on. Every change described here is a static edit, reasoned from source, and must be compiled and tested on Linux before any of it is believed.

Specifically outstanding:

  • The eBPF changes can fail the kernel verifier at load time. The probe now reads a variable-length __data_loc field, which is exactly the kind of bounds-dependent access the verifier rejects. No amount of reading reveals this; only loading it does.
  • Fifteen unit tests are written and unrun — five in record.rs (round-trip, per-field tampering, the field-boundary regression, key evolution, wrong root key), nine in the collector (including truncation-as-gap, path traversal in host ids, and the COL-1 regression), one in the shipper. verify.py --selftest covers the Python side.
  • The performance figures are derived by inspection, not measured. Perf ring headroom and RSS are computed from struct sizes and page counts.
  • The collector has no TLS of its own and expects a terminating proxy. There is no dashboard; status and verify are CLI only, and alerts go to stderr, which means the journal. Nothing pages anyone.

9.1Suggested order of work

  1. Compile the workspace on the target kernel; load the probe and confirm the verifier accepts it.
  2. Run the test suites, including verify.py --selftest.
  3. Generate a log, tamper with it deliberately, and confirm verify.py reports each class of tampering.
  4. Enroll a host against a collector, ship, then delete the tail of the log and confirm the gap is reported.
  5. Measure the resource figures in §6.2 under a realistic exec load rather than trusting the estimates.
  6. Then decide on SEN-2 — additional probes are the largest available increase in coverage, and the sealing work applies to them unchanged.
